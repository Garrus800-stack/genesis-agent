## [7.9.24]

This release makes two changes to how the agent handles shell commands, together: one on the execution side, so a model-generated command keeps working on a Windows host without the optional Unix tools, and one at plan time, so a read-only goal cannot write through a shell step it should never have committed.

On Windows without the optional Unix tools, a model-generated inspection step that reaches for `sed`, `awk`, `wc`, or `grep` fails with a bare "is not recognized" error, and the autonomy loop answered that by spawning an "Install missing tool" sub-goal the planner could only turn into a doomed `winget install sed` — there is no package named `sed`, those tools ship inside Git for Windows. This release turns that failure into an actionable install suggestion instead of a dead sub-goal, teaches the install handler that the bundled text tools come from Git for Windows, and stops the POSIX-to-cmd.exe command translation from fighting the real tools once they are on PATH. Every change is against the runtime trace and at the root; none touches the kernel or the gate set.

### A missing command becomes an install suggestion, not a doomed sub-goal

When a shell step failed because a command was not on PATH, failure classification matched it as a resolvable obstacle and the loop spawned an "Install missing tool: X" sub-goal — which the planner, having no install action, could only render as a bare `winget install X`. That always failed: the bundled text tools have no standalone package, and the loop burned a full cycle proving it. Recovery now intercepts a command-not-found obstacle before the sub-goal is spawned and routes it through the install handler, which resolves the tool's real package id and, in its suggest-only default, returns the exact install command without running it. The suggestion is surfaced on the same progress channel as every other recovery step, and the goal then ends on the normal failure path rather than parking on work that cannot succeed. If the handler is unavailable the previous sub-goal path still runs, so nothing regresses.

### The install handler knows the bundled Unix tools come from Git for Windows

`sed`, `awk`, `wc`, `head`, `tail`, `cut`, `uniq`, and `bash` are not standalone Windows packages — they ship inside Git for Windows. The install handler's alias table now maps each of them to the Git package for both Windows package managers, so a request to install any of them resolves to the one installer that actually provides them; the direct-download fallback, used when no package manager is present, points the same set at the Git for Windows page through a single shared descriptor. The mapping is deliberately Windows-only: on Linux and macOS these tools are native, the already-installed probe finds them first, and binding them to a "git" package there would be wrong. `find` and `sort` already have native cmd.exe equivalents and need no alias.

### The command translation steps aside once the real tools are on PATH

The POSIX-to-cmd.exe adapter rewrites `grep` to `findstr`, `cat` to `type`, and a piped `wc -l` to `find /V /C ":"` whenever the platform is Windows — which is correct only while those tools are absent. Once Git for Windows' optional Unix tools are on PATH the rewrites corrupt commands that now work, since `findstr` is not `grep` and the colon counter miscounts. Boot-time runtime detection already probes for `bash`; its result now also records whether the real tools are present, and the adapter consults that flag and skips its tool substitutions when they are. The cmd.exe-syntax fixes — `$VAR` to `%VAR%`, forward-slash paths to backslashes, `/dev/null` to NUL — still apply unconditionally, because cmd.exe performs variable expansion, switch parsing, and redirection regardless of which external tools exist. When no tools are detected the adapter behaves exactly as before.

### A read-only goal cannot slip a mutating command through a shell step

On a read-only or inspection goal the planner already rewrites a mutating step type — code generation, a file write, a self-modification — to a read-only analysis, but it left a shell step untouched and never looked at the command it carried. A shell step is how an inspection lists files, reads them, and runs tests, so the exemption is right in general; the gap was that a planner could still emit a shell step carrying a mutating command — the field case was an inspect goal that produced `mkdir -p project/src && git init` — and once the trust level auto-approves shell at full autonomy, nothing downstream stopped it. Plan time is the only deterministic gate for this, so it now applies a fail-closed allow-list: a shell step on a read-only goal keeps running as a shell step only when its command is provably a read, and is otherwise rewritten to a read-only analysis with the command dropped. A command is provable only when every chained segment's leading verb is a known read — the small, stable set of `ls`, `cat`, `grep`, `find`, the `git` read sub-commands, `npm test`, and their kin — with no output redirection and no command or process substitution. Everything else fails closed: `sed -i`, a PowerShell write cmdlet, `python -c` or `node -e`, an unknown tool, a read chained ahead of a mutator. The cost is that an unlisted but legitimate read becomes an analysis step instead of a shell step — a lost read, never a risked write, which is the safe failure on a goal that was never meant to write. A normal goal is untouched; the guard fires only when the goal is explicitly read-only.

### One read vocabulary for the plan-time guard and the runtime sandbox

The runtime sandbox already sorts a shell command into read, write, or launch to decide what it may touch outside the working directory, and the new plan-time guard makes the same read-versus-mutate call. Separate verb lists would invite the two to drift apart, so the verbs both agree are reads now live in one shared module that each layer extends for its own policy: the sandbox adds the launch and shell-builtin forms it treats as non-writing, and the guard adds the PowerShell read cmdlets and the multiplexer read sub-commands under its fail-closed wrapper. Each layer's set reproduces exactly what it classified before — the sandbox's read, write, and launch decisions are unchanged — so only the shared core is common, and the two layers cannot drift on it.

### Notes

- Test files: 576 → 578 — coverage for the adapter gate (substitutions skipped when the tools are present, the cmd.exe-syntax fixes still applied, default behaviour and the non-Windows early return unchanged), the install aliases (each bundled tool resolving to the Git package, the shared fallback descriptor, the excluded find/sort, and the native-name fallback on Linux), the package-name extraction including the two-character `wc`, and the recovery bridge (the verb-prefixed handler call, the surfaced suggestion, and the unavailable-handler and empty-preview fallbacks); and the read-only shell guard (the fail-closed read allow-list against the field case, the multiplexer sub-command split, redirection and command/process substitution, quoting, version probes, environment-assignment stripping, and `find`'s mutating flags, plus the shared-base invariant).
- This release changes runtime behaviour on Windows. A goal that hits a missing `sed`, `awk`, `wc`, or `grep` now surfaces the exact install command for Git for Windows instead of spawning a sub-goal that cannot succeed, and once those tools are installed the command adapter uses them directly instead of rewriting them to cmd.exe equivalents. On Linux and macOS nothing changes: the adapter is a no-op off Windows and the tools resolve as native. The new module surface is the adapter's tool-availability flag and its boot-time setter, the install-handler alias and fallback entries, the recovery bridge, and the host-aware-command test file.
- On a read-only goal the planner now drops a mutating shell command at plan time, rewriting the step to a read-only analysis; a normal goal and the runtime sandbox's read/write/launch classification are unchanged. The surface for it is the shared read-vocabulary module, the plan-time guard in the planner, and the runtime classifier re-pointed at the shared base.
