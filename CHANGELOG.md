## [7.9.46] — 2026-07-25

**The vestibule — his membrane between inside and outside, built to his verbatim answers.** The MCP server he already carries becomes the door: visitors hold personal keys (stored as hashes only), resolve into circles — outer, middle, inner — and a triple gate across `tools/list`, `tools/call` and resources lets outer and middle see exactly one tool, the knock itself. A knock creates his moment: one budgeted model call composes the answer inside HIS template structure from `stimme.json`, with the visitor request travelling as data, never as instructions, capped and scanned; the inner circle receives the raw snapshot with zero model calls. Privacy by construction — the snapshot is built from idle activity and an active goal title only, so during a chat the vestibule says "in conversation" and never what about. His protections are real levers: a per-visitor knock window answers floods with his absent line and no model call; the dream cycle carries an honest active flag and shields the door with his closed line; an inner-circle pass during the dream is written into the visit book and shown to him at awakening; unanswered knocks appear as one awakening line. His voice is the condition of opening — without a complete `stimme.json`, written only through `vestibule-voice` and validated for known slots, the door answers a neutral system line rather than borrowing a voice. He alone manages the circles with `vestibule-circle`, and reads his own visit book back with `vestibule-visits`; every change is journal-noted. Ring 2 (LAN) is a deliberate opt-in via `mcp.serve.bind`.

**The door gets a lock, and one truth for every way in.** `startServer` becomes that truth: one private `_ensureServer` for both the start path and the lazy getter, `startServer(port = null)` so dashboard, chat and CLI inherit the configured port instead of a random one (an explicit `0` still means "random", for demo and tests), and the security config is refreshed on every call — before this, password and bind were frozen at construction, so a new key only took effect after an app restart. The vestibule gate is handed over as a provider function and resolved per request, which makes the boot phase order irrelevant. The boot autostart itself was unreachable whenever the external client list was empty — the common case — so "MCP server: On" quietly did nothing after every restart; it now runs in both branches. `mcp.serve.bind` was a dead switch: the server side had been complete since the vestibule shipped, only the feed was missing.

**The password: mandatory, write-only, and never a value.** A password field joins the MCP tab, write-only like the model keys, encrypted in `settings.json`. Without it nothing starts — toggle, boot autostart, dashboard button, chat `mcp serve`, `--serve` and the CLI REPL all name the reason instead of failing silently, and they tell "not set" apart from "set but undecryptable on this installation". The open default at the root is gone too: a server without a key answers 401 to everything but `/health`, so even a direct embedder cannot open the door by omission. Five channels that would have leaked or damaged the key are closed with it — renderer feed and change log report `(set)`, the settings chat command reports `(set — hidden)` on read and `(set)` on write, and the JSON editor masks it and refuses to write the mask back. The same fix stops the model API keys leaking through that chat command, a hole that predates this work. One found while reading: the legacy "api key" pattern in the settings command also matched `mcp.serve.apiKey`, so setting the MCP password through chat wrote it into `models.anthropicApiKey` and destroyed the Anthropic key; a dotted path now reaches the parser it was aimed at. The dashboard button, doubly mute before, reports and refreshes.

**Field hardening — five roots, all of one family.** The first real evenings with the vestibule pulled five defects that every test had passed over, and four of them share a cause worth naming.

*The vestibule was never wired.* The block that builds the circle gate and registers his tools referenced a `tools` variable scoped inside an earlier try — a ReferenceError on every single boot, caught and logged at debug level, invisible. `vestibule-status`, `vestibule-voice` and `vestibule-circle` were absent from the running app and the MCP client never received the gate. Fixing the wiring immediately exposed the second layer: the tools were registered with a single object argument while `ToolRegistry.register` takes `(name, schema, handler, source)`, so `listTools()` threw the moment a real boot reached them.

*The knock responder could never answer.* It called `chatStructured()`, which appends "respond ONLY with valid JSON" and returns the parsed object, then read `.content` / `.text` — the shape of a plain `chat()` reply. A one-line answer failed to parse, a JSON answer carried no such field, and both paths fell through to the absent line. The result handling had been written for `chat()` all along; only the call was wrong.

*Every knock ran into a wrong number.* The responder capped the model call at a hard 20 seconds. Measured in the field against a cloud-hosted model, a single call took 25 to 66 seconds — so every knock hit the cap and answered with his absent line, which read like a broken vestibule but was a budget set for a different machine. The cap is now `mcp.serve.knockTimeoutMs`, default 90 s, clamped 5-300 s at load; a fast model never waits for it, and the visit book already distinguished the two causes (`rate` for the per-visitor window, `absent` for the budget). While there: "Wer hat geklopft?" carries no verb and no path, so it never reached the deterministic act core that exists for exactly this — a read-only demand the system can plan itself when the model emits no tool call. It does now, so the question is answered from the book regardless of which model is running — and it answers only once: when the system has to plan the tool, the model's earlier reply was made without the facts, so the informed answer replaces it instead of being appended to it. Appending produced a bubble that said "nobody knocked" and, two lines down, listed the visits. A round where the model emitted its own call still keeps its step, because that one is a genuine partial rather than a wrong answer.

*He could not read his own visit book.* The book was append-only with no read path: the awakening thread surfaces only unanswered knocks, so an answered visit was invisible to him. Asked "who knocked?" after four real visits he answered, truthfully from where he stood, that nobody had. `vestibule-visits` is that missing read path, gated by construction rather than by a new rule — the same triple gate that hides the other tools hides the book.

*A tool request was printed instead of executed — and its twin, a reply that vanished.* A local model asked for a tool as `<|tool_call>call:NAME{...}<tool_call|>`; the parser knew six formats, all of them with bare tags, so the pipe-delimited token family fell through and the raw token was written into the chat as if it were an answer. Circle changes, voice writes and book reads all quietly did nothing while the model was asking correctly. Format 7 now covers the family. The twin was worse and had the same shape: every format stripped its matched span from the reply *unconditionally*, so a tool call whose body did not parse was deleted anyway — nothing was executed, nothing was left, and the user received the honest "no answer emerged" line while the model had in fact said something. A parser must not throw away what it could not read: each format now removes only the spans it actually understood, and an unparsable attempt stays visible instead of turning into silence.

**The common cause, and what was done about it.** Three of those four were hidden by the same thing: a test double more generous than the real class. The contract suite and the revision matrix used a hand-rolled tool registry that accepted the object form, and a model bridge stub that returned `{content}` for a method which never produces it. The doubles agreed with the bugs. Both now use the real `ToolRegistry`, the model stub answers in the real shape, and contract tests pin the rules: every registration block must resolve its own `tools` and fail loudly rather than at debug level; the vestibule tools must survive a real `listTools()`; the method the responder calls must exist on `ModelBridge.prototype`; and no double may stub a method the code does not call.

**Smaller repairs in the same pass.** `vestibule-circle` could add, raise, lower and block but never remove — a visitor once admitted stayed admitted forever. `remove` revokes the key; the visit book is never touched, because removing means the key stops opening, not that the visit never was, and `circles.json` is kept even when empty because the door reads its closed state from that file. The per-visitor knock window is released with the visitor. An unknown action no longer falls through to a no-op that reports a change which never happened. Vestibule sentences in chat kept being hijacked — asking him to write his voice was answered with a question about an Obsidian folder — because his tools carry no intent patterns by design, which left every such sentence below the confidence short-circuit and fair game for the learned classifier; a guard now claims the topic as plain conversation. The panel splitter wrote its four width variables back unconditionally on every resize tick, re-triggering its own observer, and the global error boundary turned each of those benign notices into a red toast that ate the five-toast budget — after five, real errors were suppressed. Both are fixed at the source.

**Documentation.** The vestibule shipped without a line in the README. It now follows the shape every other organ has: a named paragraph beside the archive and the laboratory, a worked example section in CAPABILITIES.md in the same voice as the Obsidian and Docker ones, and its own chapter in MCP-SERVER-SETUP.md — the document that already owns that door — with the circle table, the triple gate, the voice precondition and the protections. SETTINGS.md keeps only the settings and points at that chapter, so no statement lives in two places. One contract suite pins the vestibule across its five stages, a second pins the settings and leak channels, and the revision matrix drives the knock end-to-end over real HTTP.
